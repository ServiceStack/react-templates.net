[Choose your database](/docs/next-saas/getting-started/choose-your-database) comes first: it sets
`DB_PROVIDER`, which selects the database this page starts and the one your deployment uses.

## Prerequisites

Install:

- .NET 10 SDK;
- Node.js 24 or a compatible current LTS release;
- npm;
- SQLite CLI for the diagnostic and verification scripts;
- Docker or Podman, when `DB_PROVIDER` is PostgreSQL, MySQL, or SQL Server;
- Git.

Stripe CLI is optional until the Stripe sandbox step. No database client tools are required:
`scripts/dev-db.sh` runs the database in a container and `./scripts/dev-db.sh shell` opens a
client inside it.

Confirm the local toolchain from the repository root:

<CopyBlock>{`./scripts/doctor.sh`}</CopyBlock>

Warnings about Stripe or email are expected for a new local checkout. Errors should be resolved before continuing.

## Install dependencies

Install the browser dependencies and the small Node toolchain used by the ASP.NET host:

```bash
cd MyApp.Client
npm install

cd ../MyApp
npm install
```

NuGet packages are restored automatically by `dotnet build` or `dotnet watch`.

## Start your database

<CopyBlock>{`./scripts/dev-db.sh up`}</CopyBlock>

This runs the provider named by `DB_PROVIDER` in `.env` and writes the local connection back
into that same private file, which the application applies in Development. The source-controlled
`MyApp/appsettings.Development.json` stays on its SQLite default. For a server provider it
uses the same image, database name, unprivileged login, and initializer scripts the deployment
uses, so the two environments cannot drift. SQLite starts no container and needs no setup.

`./scripts/dev-db.sh status` shows the provider, container state, and connection target at any
time. [Choose your database](/docs/next-saas/getting-started/choose-your-database) explains the
full workflow, including configuring the same provider for production.

## Start the application

```bash
cd MyApp
dotnet watch
```

![Running dotnet watch in Local Development](/img/next-saas/dotnet-watch.png)

Open `https://localhost:5001`. ASP.NET Core owns the public origin and starts the Next.js development process automatically. Browser API requests therefore use the same origin as Identity cookies and ServiceStack APIs.

The first Development start with no application database:

1. creates the ASP.NET Core Identity schema;
2. runs the OrmLite SaaS migrations;
3. seeds Free, Pro, Business, and Enterprise plans;
4. creates development users;
5. creates a personal organization and Free subscription when a seeded user first signs in.

## Check the application

After signing in, verify:

- `/dashboard` loads the active organization once without repeated API calls;
- `/documents` permits a small supported file upload, and accepts several files at once;
- `/usage` displays document and storage usage;
- `/settings` displays organization lifecycle controls for an Owner;
- `/admin` opens the Operations Center for `admin@email.com`; its side menu links to the focused `/admin/*` routes;
- `/up` and `/ready` return healthy responses.

API contracts and diagnostic tools are available at `/scalar/v1`, `/ui`, and `/admin-ui`.

## Recreate local state

This template is designed to recreate itself from an empty development database. Stop the application, then run:

<CopyBlock>{`ASPNETCORE_ENVIRONMENT=Development ./scripts/reset-dev.sh --yes`}</CopyBlock>

The script follows whichever provider is running. On SQLite it validates exact paths before removing `MyApp/App_Data/app.db`; on a server provider it recreates that database's container volume through `scripts/dev-db.sh`. It always removes `MyApp/App_Data/files` and then runs the migration task. It refuses to run outside Development or without `--yes`.

ServiceStack Background Jobs and request logs use separate generated SQLite databases under `MyApp/App_Data/jobs` and `MyApp/App_Data/requests`, whichever provider holds application data. They are operational diagnostics rather than billing or enforcement records, they are development artifacts here, and they can also be removed while the application is stopped.

## Common setup problems

### The HTTPS certificate is not trusted

Trust the ASP.NET Core development certificate:

<CopyBlock>{`dotnet dev-certs https --trust`}</CopyBlock>

### Port 5001 or 3000 is already in use

Stop the previous `dotnet watch`, `dotnet run`, or Next.js development process before starting another instance.

### The schema does not match the code

During template development, recreate the local database with `reset-dev.sh`. Derived production applications should add a forward migration instead.

### The application will not connect to the database

`./scripts/doctor.sh` reports the effective local provider and warns when it disagrees with `DB_PROVIDER`, and `./scripts/dev-db.sh status` shows whether the local database is running. [Choose your database](/docs/next-saas/getting-started/choose-your-database#troubleshooting) lists the specific startup errors and their causes.

### Paid checkout is unavailable

That is expected until Stripe sandbox keys and plan Price IDs are configured in step 6.
